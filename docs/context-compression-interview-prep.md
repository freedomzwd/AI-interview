# 上下文压缩 · 面试准备手册

> 配套设计文档：`docs/context-compression-design.md`
> 适用岗位：AI 应用开发 / Agent 开发
> **当前状态：方案已设计，代码未合入。** 表述时必须守住这条线，见第 6 节。

---

## 1. 先立住四个底层事实

这四个是全部推导的地基。面试时无论从哪切入，都要能立刻回到这四条。

### 1.1 LLM 是无状态的

模型不记得上一次调用。所谓「对话」，是每次请求把你的全部历史重新拼进 prompt。这句话听起来像常识，但它推出三个结论：

- 上下文长度 = 你的成本，不是模型的记忆
- 历史越长，每次调用的输入越大，这是**必然**的重复传输
- 「让模型记住」本质上是「你替它记住，再喂给它」

**面试价值**：能一句话说清这点，说明你知道自己在优化什么。说不清的人会把「上下文管理」和「微调」「RAG」混在一起。

### 1.2 成本是随轮次累积的

第 i 轮要传前 i-1 轮的内容。

- **全量保留**：n 轮总输入 ≈ `n²/2 × 单轮长度` —— 平方增长
- **固定窗口**：n 轮总输入 ≈ `n × 窗口大小` —— 线性
- **摘要 + 窗口**：同样是线性，但信息保住了

这三者是一条清晰的演进链。**你的项目现在处在第二阶段（`chat_history[-6:]`），目标是第三阶段。**

### 1.3 长上下文不等于好效果

Lost in the Middle（Liu et al., 2023）的结论：当关键信息位于长上下文中段时，模型召回率显著低于位于开头或结尾时。

推论：**把全部历史塞进去，不但贵，还可能更差**。上下文不是越多越好，是信噪比越高越好。

**面试价值**：这是唯一一条能引用论文的知识点，用来反驳「我有 128k 窗口为什么还要压缩」最有力。

### 1.4 压缩必须是有损的

无损压缩在 LLM 上下文里不存在——token 数量本身就是信息量。所有压缩策略都在选择「丢哪一类信息」。

所以问题从来不是「要不要丢」，而是「**丢哪一类损失最小**」。这句话是整套方案的立意。

## 2. 六种策略与各自代价

对应上一张权衡图。每一种都要能说出「省在哪、丢在哪」。

| 策略 | 做法 | 省什么 | 丢什么 | 适用 |
|---|---|---|---|---|
| 全量保留 | 不处理 | 不省 | 不丢 | 短会话、调试期 |
| 滑动窗口 | 只留最近 K 轮 | 大量 token | 早期全部内容 | 只依赖近期上下文的场景 |
| 摘要压缩 | 旧轮次转成摘要 | 大量 token | 细节、原话 | 长对话、需全局一致性 |
| 结构化抽取 | 抽成字段/槽位 | 极多 token | 除字段外的一切 | 有明确 schema 的任务（你的项目） |
| 外部化 + 检索 | 原文存库，按需召回 | 大量 token | 召回失败的那部分 | Agent、知识密集场景 |
| 专用压缩模型 | 小模型做 token 级压缩 | 极多 token | 低权重 token | 有专门基础设施的团队 |

**你的选择落在「摘要 + 结构化抽取」之间**，这正是面试图里标圈的位置。要能解释为什么不在两端：

- 不在左下（全量）：成本线性变平方，且中段信息召回差
- 不在右下（纯截断）：跨题一致性丢失，这是面试评分的硬需求

## 3. 你的方案，逐条对应到知识点

每一行都是「设计决策 → 背后的原理 → 面试怎么讲」。

### 3.1 双区结构：冻结摘要 + 滑动原文

```
[ 候选人卡 400t ][ 摘要区 600t ][ 最近 3 轮原文 1400t ][ 当前题 800t ]
       固定              只增不改            滑动                固定
```

**原理**：摘要区一旦写入就冻结（靠锚点），只在窗口溢出时增量更新。避免「每轮重新摘要」带来的抖动——同一段内容被反复压缩，每次摘要措辞略有不同，几轮后整个摘要会漂移失真。

**讲法**：「摘要区是冻结的，不重算。这跟数据库的 WAL 一个思路——已经落盘的段不回头改，只往后追加。」

### 3.2 预算分区

总预算 3500 token，五个区各自独立配额。

**原理**：整段统一砍会导致「哪个区最胖就砍哪个」，而胖的往往是简历（因为长），结果砍掉最该保留的背景信息。分区配额让每个区按业务重要性分配。

**讲法**：「按区给配额，不是按总量砍。因为砍总量的时候，被砍的一定是最长的那个——通常是简历，但简历恰恰是最不能丢的。」

### 3.3 摘要要带 schema

```json
{
  "covered_topics": ["已考察的技术主题"],
  "correct_points": ["答对的要点"],
  "weak_points": ["答错或含糊的点"],
  "open_threads": ["提出但未深挖的方向"],
  "contradictions": ["与其他轮次冲突的内容"]
}
```

**原理**：通用对话摘要输出的是「聊了项目经验、问了 Redis」这类平铺描述——对评分毫无用处。面试评分真正依赖的信号只有三个：**错在哪、还欠什么追问、哪里前后矛盾**。把领域知识编码进 schema，是自研相对通用组件的唯一增量。

**讲法**（这段是全场加分点）：「通用摘要器会告诉我『他们聊了 Redis』，但我要知道的是『他说 Redis 做了缓存击穿，但说不出布隆过滤器的误判率，这里是个洞』。所以摘要不能是自由文本，得有字段。字段就是我的领域知识。」

### 3.4 幂等锚点

`interviews.summary_upto_index` 记录已压缩到的题号，单调递增。

**原理**：压缩可能被重复触发——SSE 断流重试、用户重复提交、Celery 任务重跑。没有锚点，同一段内容会被反复压进摘要，两三次之后摘要里全是重复表述，信息密度崩溃。

**讲法**：「摘要操作必须幂等。我用一个单调递增的游标记录压到哪了，写入和游标更新在同一个事务里。重复触发时，游标之前的内容不会再进摘要。」

**为什么这个点值钱**：它把问题从「LLM 效果」拉回到「工程正确性」，而后者才是工程岗要考的东西。

### 3.5 失败降级，不阻塞主流程

摘要 LLM 超时 → 不写库 → 本轮用纯窗口 → 打 `fallback` 指标。

**原理**：压缩是优化路径，答题是主路径。优化失败不能拖垮主流程。面试是实时交互，等 3 秒摘要比丢一点上下文糟得多。

**讲法**：「压缩失败就降级回纯窗口，面试继续。指标上能看到 fallback 比例，超过 5% 说明摘要调用不稳定，那是另一个问题，但不该让用户感知。」

### 3.6 Agent state 的压缩逻辑完全不同

这是你的项目里第二个压缩点，也是最容易被忽略、最能拉开差距的部分。

| | 对话历史 | Agent state |
|---|---|---|
| 数据性质 | 过程数据，用完即弃 | 任务资产，要能恢复 |
| 压缩目标 | 减少 prompt token | 减少快照体积 |
| 手段 | 摘要 | 外置 + 引用 |
| 正确性要求 | 允许有损 | 不允许丢 |

**你的具体问题**：`scout_results` 用了 `operator.add` 做 reducer，三个并行分支的完整结果（每个含 5 条带 JD 全文的岗位对象）全部追加进 state，`merge_positions` 只取前 3 条，剩下的成为死数据永久驻留 checkpoint。而 `thread_id` 内嵌 uuid，每次 run 都是新 thread，没有 TTL 清理。

**讲法**：「对话的压缩是把内容变小，state 的压缩是把内容搬走。因为 state 要支持中断恢复，你不能靠摘要去『概括』一个需要精确重建的状态。我的做法是把 JD 全文这类大字段外置到 Store，state 里只留引用。」

## 4. 三个表达层次

### 4.1 三十秒版（自我介绍 / 项目概述时用）

> 「LLM 是无状态的，每轮对话都要把历史重新发一遍。我的面试系统里，接近一半的输入 token 花在重复传同一份简历上。原来我靠截断最近 6 条消息把成本压成线性，代价是前 3 题的内容直接丢了，模型没法判断候选人前后是否矛盾。我改成双区结构：早期轮次压成带 schema 的摘要，最近 3 轮保留原文，总预算封顶。」

四句话，四个功能：立地基 → 给数字 → 承认代价 → 给方案。

**注意最后一句不要加「效果提升了 xx%」**，没测过就别编。

### 4.2 两分钟版（被问「详细说说」时用）

在三十秒版基础上，按这个顺序展开：

1. **问题定性**：「先说清楚这不是容量问题。10 题大概 20k token，DeepSeek 是 128k 窗口，塞得下。问题在成本和信噪比。」
2. **成本结构**：「单次 prompt 大概 3000 token，其中简历占 1400——接近一半是重复传输。10 题下来这笔钱白花。」
3. **截断的代价**：「我原来用 `[-6:]`，相当于只留最近 3 轮。第 4 题往后，前面的内容永久丢失。总分算得出来，但『第 2 题说用 Redis 解决击穿、第 8 题又说不会用 Redis』这种矛盾判不出来。」
4. **改法**：「双区。早期轮次进摘要区，摘要不是自由文本，是五个字段的 JSON——考察了什么、答对什么、答错什么、哪些方向提了没深挖、哪里前后矛盾。最近 3 轮保留原文。总预算 3500 token 封顶。」
5. **工程约束**：「摘要要幂等，用一个单调递增的游标记录压到哪了，重复触发不会重复压。摘要调用失败就降级回纯窗口，不阻塞答题。」

### 4.3 五分钟版（深挖时用）

在两分钟版之后加三块：

- **为什么不用现成组件**：`trim_messages` 只能裁不能压；`ConversationSummaryBufferMemory` 在 0.1 之后移出主路径；LangMem 的 `SummarizationNode` 是通用摘要，没有领域 schema。自研的实际增量只有两点——schema 和锚点，但这两点恰好是这个场景的全部价值。
- **Agent 侧**：state 的膨胀和对话不是一回事，说 3.6 那张对比表。
- **怎么验证**：三项 A/B。第 8 题时的 prompt token（看成本）、评分与人工标注的一致率（一票否决）、端到端 p95（摘要多一次调用，可能涨 200ms，涨了就改异步预生成）。

## 5. 高频追问与答法

按被问概率排序。每题答案控制在三句以内，说完就停。

**Q1：你有 128k 窗口，为什么还要压缩？**
> 窗口够，成本和信噪比不够。而且长上下文中间段的信息召回率明显低于两端，塞满反而更差。我压的不是容量，是重复传输和噪声。

**Q2：直接截断不行吗，为什么要摘要？**
> 截断够用于「只看当前题」的评分。但我的报告要跨题判断一致性，前面丢光了就判不出矛盾。截断是把成本从平方压到线性，摘要是在同样线性成本下把信息保住。

**Q3：摘要会不会丢关键信息？**
> 会。所以我不做自由摘要，用固定字段。字段是我从评分逻辑里反推的——错在哪、欠什么追问、哪里矛盾。另外只在窗口溢出时触发，能留原文就留原文。

**Q4：摘要本身也要调 LLM，不是又加成本了？**
> 加。但触发频率低，10 题大概触发 1 到 2 次，单次输出 500 token 以内。每轮省下的 1000 token 覆盖它绰绰有余。真要再省，摘要可以挪到上一轮响应之后异步预生成。

**Q5：怎么保证不重复摘要？**
> 单调递增的游标 `summary_upto_index`，只有大于游标的轮次参与压缩，写入和游标更新同事务提交。

**Q6：并发或者用户重复提交怎么办？**
> 游标做乐观锁，或者直接 `SELECT FOR UPDATE` 锁这一行。压缩是低频操作，加锁代价可以忽略。

**Q7：为什么不用 LangChain 的 trim_messages？**
> 它只按 token 裁剪，裁掉的不可能恢复。我需要的是压缩，不是裁剪。

**Q8：那用 LangMem 的 SummarizationNode 呢？**
> 它是通用对话摘要，输出是自然语言。我需要的是带字段的结构化摘要，通用组件给不了这个 schema。

**Q9：怎么证明压缩之后效果没变差？**
> 三项 A/B。token 曲线看成本，p95 看延迟，评分与人工一致率看质量。第三项是一票否决——省 token 不能拿评分质量换。

**Q10：流式输出怎么处理？摘要在流中间跑吗？**
> 不能插在流里。要么在流开始前同步跑完，要么挪到上一轮响应结束后的后台任务。我倾向后者，用上一轮返回的『下一题』响应做触发点。

**Q11：如果对话到 100 轮呢？摘要区也会爆。**
> 分层摘要，对已冻结的摘要再做一次摘要。或者切到外部化——原文全量落库，按需检索相关轮次。后者在超长会话里更稳，因为检索是无损的。

**Q12：你说 state 也要压缩，那和对话压缩什么区别？**
> 对话是过程数据，压完就扔，可以有损；state 是任务资产，要能中断恢复，不能有损。所以 state 靠外置加引用，不靠摘要。

**Q13：为什么不直接把简历换成引用，每次去查？**
> LLM 只能吃文本，必须序列化进 prompt。能优化的是体积——把 2000 字压成 400 字的卡片，不是去掉。

**Q14：摘要和原文冲突了怎么办？**
> 摘要只做减法不做改写，原文里的事实不会被摘要改掉。而且 contradictions 字段是显式记录冲突，不是消解冲突——冲突本身就是要报给面试官的信息。

**Q15：这套方案有什么缺点？**
> 加了一次 LLM 调用、两列迁移、一个降级分支。摘要质量依赖 prompt，得拿样本调。另外它对「短会话」是纯成本没有收益，所以得挂开关，5 轮以内的面试直接走原路径。

## 6. 表述红线

以下五条，说错任何一条都会被追问到崩。

| 不能说的 | 为什么 | 应该说的 |
|---|---|---|
| 「我的系统 token 是平方增长」 | 你有 `[-6:]` 截断，实际是线性的。面试官一算就发现你说错了 | 「我用截断换来了线性成本，代价是信息丢失」 |
| 「优化后效果提升 30%」 | 没测过就是编。追问一句测法就露 | 「方案设计了，A/B 还没跑」 |
| 「我用了 LangChain 的 memory 组件」 | 你没用 | 「我自己写了摘要器和锚点，比通用组件多两个约束」 |
| 「因为上下文窗口不够」 | 128k 够用，判断错了 | 「窗口够，成本和信噪比不够」 |
| 「这是业界最佳实践」 | 没有最佳实践，只有权衡 | 「在我的约束下这个点最优，换成超长会话我会选外部化」 |

**最重要的一条**：如果被问到「上线了吗、数据怎么样」，直接说「方案做完还没合，验证排在下一步」。这句话不丢分——**应届生被扣分的从来不是「没做完」，是「讲得像做完了但答不上细节」**。

## 7. 想加分就再补这三句

面试官听完会觉得「这人想得比别人深一层」的三句话：

1. **关于动机**：「我先判断这个场景到底缺什么。容量不缺、成本缺、信噪比缺。如果按『窗口要满了才压缩』去设计，会做出一个激进摘要的方案，反而把评分质量搞坏。」

2. **关于取舍**：「摘要的字段是我从评分逻辑倒推的，不是从通用的对话摘要模板抄的。这个 schema 就是领域知识，也是自研唯一说得过去的理由。」

3. **关于边界**：「这套东西对 5 轮以内的面试是纯成本。所以我挂了开关，短会话走原路径。任何优化都得知道它在哪儿不适用。」
