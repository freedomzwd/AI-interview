## 1. Agent / LangGraph 方向（最高频，必问）

### Q1：你这个 Agent 具体是怎么用 LangGraph 编排的？画出状态图给我看

**考察意图**：判断你是真上手写过 LangGraph，还是只见过教程。真写过的人能立刻说清节点、边、状态 schema、条件路由。

**参考回答**：
> 岗位匹配 Agent 是一个 `StateGraph`，状态类叫 `PositionAgentState`。主链路是 `load_context → resume_analyst → 条件路由`。`load_context` 负责把简历、岗位模板、长时记忆装进 state；`resume_analyst` 做简历画像抽取；然后我加了一个 `_scout_categories` 的条件边，根据画像里的技术栈把流程分发到不同的岗位大类分支去做匹配，而不是一条直路走到底。图编译时挂了 `AsyncPostgresSaver` 做 checkpointer、挂了 `PostgresStore` 做长时记忆，图名字是 `position-match`。

**追问链**：
1. *为什么用条件边而不是一个节点干完？* → 要点：不同技术栈候选人的岗位模板集合不同，一条路要把所有模板都塞进 prompt，token 爆炸且噪声大；分流后每支只喂相关模板，召回更准。
2. *state 里放什么？为什么这么设计？* → 要点：输入类（resume_id、岗位范围）+ 中间产物（candidate_profile、召回候选）+ 输出类（推荐岗位、面试重点）+ 控制类（`completed_steps`、`errors`）。区分开是为了可恢复、可观测。
3. *checkpointer 和 store 的区别是什么？* → 要点：checkpointer 存**单次运行的状态快照**（thread 级，用于断点续跑 / 崩溃恢复）；store 存**跨 thread 的长期记忆**（用户级，比如这个候选人上次面试表现如何）。两者不是一回事。
4. *thread_id 怎么设计的？* → 要点：`position-match:{user_id}:{resume_id}:{run_id}`，用 run_id 隔离每次运行，避免同一份简历反复跑覆盖历史快照。
5. *节点抛异常了怎么办？* → 要点：节点内 try/except 把错误写进 `errors` 字段而不是直接抛出，让图能带着"部分成功"的状态走完，前端可以展示哪一步失败。

### Q2：简历上写了"面试 Agent 状态图"，面试流程的图长什么样？

**考察意图**：⚠️ **这是最可能当场翻车的问题**。简历写了"面试 Agent 状态图"，代码里只有岗位匹配图。面试官一旦让你画，你画不出来就是致命的诚信问题。

**正确策略：不要现场编，主动澄清边界。**（编了之后 Q2-Q5 会连环追问，你一定会露馅。）

**参考回答**：
> 这里我要澄清一下我简历的表述，写得不够准确。目前真正用 LangGraph 编排成状态图的是**岗位匹配 Agent**；面试环节我是在 service 层实现的，是"检索 → 组题 → 逐题打分 → 汇总报告"的顺序流程，**还没有重构成独立的 LangGraph 图**。所以准确说法是"Agent 化的流程编排"，而不是"两个状态图"。
>
> 为什么没做：面试环节是有强顺序依赖的（必须逐题拿到回答才能打分），没有复杂的分支和工具调用，用 graph 编排收益不高。但如果要支持**动态追问**和**多轮中断恢复**，我就必须把它改成图——因为只有图 + checkpointer 才能在任意一轮中断后续跑。这是我下一版的计划。

**追问链**：
1. *那你觉得面试环节改造成图，节点怎么切？* → 要点：`load_context → plan_question → ask → (interrupt 等人答) → evaluate_answer → 条件边(追问/下一题/结束) → generate_report`。
2. *为什么要用 interrupt？* → 要点：面试是 human-in-the-loop，必须在"问完一道题"处挂起等用户输入，LangGraph 的 `interrupt` + checkpointer 正好解决"消息断了、服务重启了还能接着答"。
3. *不改成图会有什么实际损失？* → 要点：无法做断点续跑、无法在评估结果差的题目上动态插入追问、状态散落在 DB 里难以做时序回放。

> **口诀**：这块主动认边界，比被问出来强 10 倍。面试官对应届生"没做完"的容忍度远高于"吹牛"。

### Q3：你说是"自适应面试"，具体自适应的机制是什么？

**考察意图**：简历写了"自适应出题、追问、难度调整"。面试官要问出你到底做到哪一步。

**参考回答**：
> 我的自适应主要体现在**面试前**而不是面试中：系统会综合简历技能、目标岗位、以及**历史面试的失分点**，动态生成这次面试的上下文——上次在"数据库索引"上失分，这次就重点覆盖这个方向。难度是通过岗位模板给出的建议难度 + 用户选择来确定，然后影响 RAG 召回的题目难度分布。
>
> 面试**过程内**的动态调整，诚实说我只做了一半：我给评分结果的 schema 留了 `follow_up` 字段，让模型判断这题答得不好时是否该追问，但这个字段目前只是被生成出来，**业务逻辑还没有消费它**——也就是追问没有真正跑通。这是我下一步要补的。难度分档也是静态传入的，不是根据答题表现实时升降。

**追问链**：
1. *如果让你把追问做通，怎么做？* → 要点：`evaluate_answer` 后判断 `score < 阈值` 且 `follow_up == true` 时，生成基于"该题参考答案的缺失采分点"的追问 prompt，插入到题目队列，`question_index` 保持不变、用子序号标记。
2. *难度动态升降怎么设计？* → 要点：连续 N 题均分 > 阈值则升档，< 阈值则降档；档位映射到 RAG 召回的 `difficulty` 过滤条件。
3. *这样会不会让不同人拿到的题目差异太大，无法横向比较？* → 要点：会。所以要么保留一条固定题组用于基准比较，要么在报告里对分数做难度归一化。这是个 trade-off，得说清。
4. *历史面试表现怎么存怎么取？* → 要点：说 `PostgresStore` 长时记忆，按 user 维度存失分标签；或者直接从 `interviews` 表聚合。

### Q4：你的 Agent 为什么不用 Function Calling / Tool Calling，而是用图节点调服务？

**考察意图**：考察你对"Agent 形态选型"的理解。这题有个陷阱——你的**旧文档**里写的是 Tool Calling Agent（5 个工具 + AgentExecutor），**新代码**是 LangGraph。面试官如果同时看过你两个版本的描述，会问这个。

**参考回答**：
> 我一开始确实做过 Tool Calling 版本：用 `AgentExecutor` 加 5 个工具（读简历、构建画像、匹配岗位、取面试重点、启动面试），靠 `max_iterations` 和 `handle_parsing_errors` 做控制。后来改成 LangGraph 是因为**可控性**。
>
> Tool Calling 的问题在于：调用顺序由模型自己决定，同样输入两次可能走不同路径；出了偏差你只能看日志猜。而我的业务流程其实是**确定的**——必须先有画像才能匹配岗位，这个顺序不该交给模型去"想"。改成图之后，顺序由代码保证，模型只负责每个节点内部的语义工作（抽取、打分），可测、可回放，还能挂 checkpointer 做断点续跑。
>
> 一句话总结：**流程确定性交代码，语义不确定性交模型**。

**追问链**：
1. *那什么时候 Tool Calling 更合适？* → 要点：工具数量多、调用顺序真的不固定、需要模型自主探索的场景（比如开放式研究型 Agent）。
2. *图编排的缺点是什么？* → 要点：灵活度低，业务一变就要改图；节点粒度设计不好会让 state 膨胀；调试比单 agent 复杂。
3. *你现在图里有几个节点？为什么是这个粒度？* → 要点：按"职责边界"而不是"API 调用"切；同一次 LLM 调用+DB 写入算一个节点，避免节点过碎导致 checkpoint 表暴涨。
4. *LangGraph 的 state 是可变还是不可变？* → 要点：节点返回的是**增量 dict**，框架按 reducer 合并进 state，所以不要直接改 state 对象。

### Q5：你的 Agent 怎么保证输出格式稳定？模型返回非法 JSON 怎么办？

**考察意图**：这是 AI 应用落地的核心工程问题，几乎必问。

**参考回答**：
> 三层防护。
>
> 第一层是 **Pydantic schema 约束**：所有模型输出必须能过 `InterviewQuestion`、`AnswerEvaluation`、`CandidateProfile` 这类 schema，字段类型不对直接判失败。
>
> 第二层是 **JSON 提取 + 一次修复**：模型经常在 JSON 外面包 ```json 代码块或者加解释文字，我先用正则把 JSON 主体抠出来；解析失败就**再调一次模型让它自己修**，只修一次，不无限重试。
>
> 第三层是**安全兜底**：修复也失败时，不抛异常给用户，而是返回一个 fallback 结构——比如题目生成失败时回退到基础题，保证面试流程不中断。这是"降级"而不是"报错"。
>
> 另外重试我用了 tenacity，指数退避、最多 3 次，应对的是网络类和限流类错误，跟格式错误是分开的两类问题。

**追问链**：
1. *为什么不直接用 OpenAI 的 `response_format=json_schema` 强约束？* → 要点：DeepSeek 兼容层对严格 schema 模式支持有限；而且结构化输出约束只能保证 JSON 合法，**保证不了语义正确**（比如 `score` 给 9.5 但内容明显不及格），所以业务层校验仍然必须。
2. *"修复一次"为什么只修一次？* → 要点：模型修不出来的通常是 prompt 或 schema 设计问题，反复修只是烧 token；一次之后直接走兜底更快也更省。
3. *fallback 会不会掩盖问题？* → 要点：会。所以 fallback 触发必须打点（我用 `LLM_REQUESTS` 的 `status` 标签区分）和记日志，否则你永远不知道线上降级率有多高。
4. *怎么监控降级率？* → 要点：看 `ai_interview_llm_requests_total{status="error"}` 占比，超过阈值就该告警——**这块我只是把指标埋了，告警规则还没配**。

### Q6：Agent 跑了多久、每一步多慢，你怎么定位？如果某次推荐结果很离谱，怎么排查？

**考察意图**：考察可观测性和排障能力。AI 应用最容易被问"线上出问题你怎么查"。

**参考回答**：
> 三个抓手。
>
> **指标层**：`ai_interview_agent_runs_total` 按 status 计数看成功率，`ai_interview_agent_node_duration_seconds` 按 node 标签看每个节点耗时，定位是模型慢还是 DB 慢。
>
> **链路层**：每次 Agent 运行有 `run_id`，LangGraph 的 checkpointer 把每个节点的状态快照落到了 PostgreSQL 的 checkpoint 表，所以我能回放整条状态链——这是最有价值的一层，能直接看到"画像是错的还是匹配权重是错的"。
>
> **日志层**：节点级日志带 run_id，记录输入输出摘要。
>
> 排查顺序：先看是**输入错**（简历解析出来的画像就已经偏了）还是**逻辑错**（画像对但匹配分数不对）。画像错就往 `resume_analyst` 节点和简历解析 prompt 查；分数错就查岗位模板的 `core_skills` 标签配置。

**追问链**：
1. *checkpoint 表会无限膨胀吗？* → 要点：会，这是真实问题。需要一个清理策略：按 run_id 保留最近 N 次、或按时间归档删除；长时记忆（store）存的是压缩后的结论，不是原始快照。
2. *节点的输入输出摘要你会存全文吗？* → 要点：不存全文，存摘要 + hash + 长度。存全文有两个毛病：一张表存所有 prompt 很快就爆；简历里有 PII，存全文是隐私风险。
3. *你项目里哪个节点最慢？* → 要点：LLM 调用节点（画像抽取、rerank）是瓶颈，DB 和向量检索都在几十毫秒量级。所以优化方向是减少 LLM 调用轮数、并行化独立调用。
4. *怎么并行？LangGraph 支持吗？* → 要点：支持，同一个 superstep 里没有依赖关系的节点会并行执行；我的 `_scout_categories` 分流出来的多个岗位大类匹配本来就可以并行。

### Q7：你的混合检索到底怎么做的？RRF 的公式写给我

**考察意图**：验证"RRF 融合"是真理解还是抄名词。能写出公式的人是真的做过。

**参考回答**：
> 混合检索 = 稠密 + 稀疏两路，然后融合。
>
> **稠密路**：用 DashScope 的 `text-embedding-v3` 把 query 和 chunk 都转成 1024 维向量，走 pgvector 做余弦相似度检索。优点是理解语义（"并发安全问题"能召回"线程安全"），缺点是专有名词、代码符号、缩写召回差。
>
> **稀疏路**：PostgreSQL 全文索引，走 `tsvector`，对关键词精确匹配强——比如搜 `GIL`、`asyncio`、`MVCC` 这种词，稠密向量经常召回不出来。
>
> **融合用的是 RRF（Reciprocal Rank Fusion）**，公式：
>
> `score(d) = Σ 1 / (k + rank_i(d))`，我项目里 `k = 60`（配置项 `RAG_RRF_K`）。
>
> RRF 的好处是**只看排名不看分数**。因为稠密路给的是余弦相似度（0~1 之间），稀疏路给的是 `ts_rank`（量纲完全不同），直接加权求和根本不可比；RRF 把两路都转成"排名"这个统一量纲，才能公平融合，而且对分数的尺度差异天然鲁棒，几乎不需要调参。

**追问链**：
1. *k=60 是怎么定的？* → 要点：k 是平滑项，防止 rank 靠前时权重过大。论文给的 60 是社区默认值，我在检索测试页对比过 20/60/100，差异不大，就保持默认。**要老实说这是经验值，不是调出来的最优值。**
2. *为什么不直接把两路分数归一化后加权求和？* → 要点：可以做（我项目里也有 `normalize_retrieval_scores`），但归一化依赖当次结果集的 min/max，**结果集一变分数就不可比**，稳定性不如 RRF。
3. *RRF 的缺点？* → 要点：丢掉了分数信息。两路都排第 1 的文档，和一个排第 1 一个排第 50 的文档，RRF 区分度有限；而且它只做"排名投票"，不解决两路都召回错的情况。
4. *RRF 之后再 rerank 的意义是什么？* → 要点：RRF 是**无监督**融合，只看相对位置；rerank 用交叉编码或 LLM 做 **query-doc 逐对精算**，能把"确实相关"的顶上来，解决 RRF 分辨率不足。

### Q8：你的 four 种检索模式（semantic / keyword / hybrid / advanced）分别什么时候用？

**考察意图**：看你有没有真的做过对比，而不是把所有模式都塞进去凑数量。

**参考回答**：
> `semantic` 纯向量，用于口语化问答；`keyword` 纯全文索引，用于已知确切术语的精确查找；`hybrid` 是 RRF 融合，是**生产默认值**（`RAG_SEARCH_MODE=hybrid`）；`advanced` 在 hybrid 之上再做两步——**查询规划和 LLM rerank**。
>
> `advanced` 的两步是：先用 `RAGQueryPlan` 让模型把用户的自然语言问题**改写成更适合检索的查询**（拆子问题、补同义词），再对 RRF 融合后的候选做一次 LLM 重排，输出带 `rerank_score` 的结果。
>
> 我的选择原则是：**默认 hybrid 兜质量，advanced 留给对精度要求高的场景**（比如给评分环节找参考答案）。因为 advanced 多两次 LLM 调用，延迟和成本都明显更高。前端管理端我做了检索测试页，可以四种模式并排对比结果。

**追问链**：
1. *advanced 延迟高多少？* → 要点：多两次 LLM 往返，通常从几百毫秒涨到 2~5 秒。所以它不能用于在线主链路的高 QPS 场景。
2. *LLM rerank 和 BGE-reranker 这类交叉编码器比，优缺点？* → 要点：LLM rerank 无需额外部署模型、能理解复杂语义指令，但慢且贵；交叉编码器快得多、可自托管，但语义理解弱一些。工程上高 QPS 用交叉编码器、低 QPS 高精度用 LLM。
3. *为什么不在所有链路都用 advanced？* → 要点：出题环节本身还有一次 LLM 生成，如果检索也用 advanced，一次面试的 LLM 调用轮数会翻倍，延迟和成本都不可接受。
4. *rerank 的 top_k 怎么定？* → 要点：先大范围召回（比如 RRF 后 20~40 条），rerank 后取最终 k。

### Q9：文档怎么切分的？chunk_size=500 / overlap=50 是怎么来的？

**考察意图**：切分策略是 RAG 的必问点，也是最容易看出"有没有真调过"的地方。

**参考回答**：
> 用 `RecursiveCharacterTextSplitter`，`chunk_size=500`，`chunk_overlap=50`。
>
> 递归切分的顺序是：先按段落（`\n\n`）切，太长再按换行，再按句子，最后才按字符硬切——**尽量在语义边界上断开，而不是按固定字数生切**。
>
> 500 这个量级的选择逻辑：太小（比如 200）单块语义不完整，"为什么用 RRF"这种问题可能答案被切到两块里，两块的向量都不完整，谁都召不回来；太大（比如 1500）一块里混了好几个主题，向量被平均掉，表达变模糊。
>
> overlap 设 50，是防止关键句正好落在切点上被劈成两半，保留一点上下文重叠。50 大约是 chunk 的 10%，是社区比较通用的比例——**我承认这是经验值，我目前没有做过系统的切分参数对比实验来选它**。
>
> 另外我的知识库文档以 Markdown 为主，标题层级本身就带结构信息，理论上用 Markdown 感知的切分器（按 H2/H3 切）效果会更好，这是我还没做的优化点。

**追问链**：
1. *overlap 会不会造成重复召回、浪费 token？* → 要点：会，且重叠区域的 chunk 语义高度相似，容易在 top_k 里占多个坑。缓解办法是相邻 chunk 去重、或者做 MMR 多样性重排。
2. *怎么科学地选 chunk_size？* → 要点：构造一批「问题 → 应召回的 chunk id」标注集，扫 chunk_size = 256/384/512/768/1024，看 Recall@k 和 MRR 的曲线，选拐点。**这正是我还没做的评估脚本的用途。**
3. *代码类文档和自然语言文档切分策略一样吗？* → 要点：不一样。代码要按函数/类切，天然语义单元是函数级，硬切会把函数体劈开导致召回片段不可用。
4. *表格和图片怎么处理？* → 要点：表格切分时容易被切碎，需要整表保留并转成 Markdown 表；图片需要多模态模型生成描述再入索引。我项目里只处理文本，这是局限。

### Q10：题库 RAG 和知识库 RAG 的参数为什么差这么多？

**考察意图**：判断你是不是在"盲调参数"，还是理解参数背后的业务目标。

**参考回答**：
> 因为它们目标完全不同。
>
> **知识库**：`top_k=4`、`min_score=0.3`。目标是"找上下文喂给模型"，宁可多召回一点，让模型自己去甄别，阈值放松是为了不漏。
>
> **题库**：`top_k=20`、`min_score=0.7`。目标是"精确召回高相关题目"，因为题目要**直接呈现给用户**，召回一条不相关的题就是明显的质量事故。所以阈值拉高、但要扩大候选量（还有 `QUESTION_BANK_RECALL_FACTOR=2` 的放大系数），召回后还要再筛。
>
> 本质区别：知识库是**中间产物**，噪声可以由模型吸收；题库是**最终产物**，噪声直接暴露给用户。**下游要不要给用户看，决定阈值松紧。**

**追问链**：
1. *0.7 这个阈值会不会太高导致召不满题目？* → 要点：会，这是实际遇到的问题。所以有 `RECALL_FACTOR` 放大候选池 + 模型补全机制（`source="ai_fallback"`）兜底——召回不够就用模型生成补齐，并标记来源，方便事后统计题库覆盖率。
2. *0.3 到 0.7 的差异你有数据支撑吗？* → 要点：老实说没有严格的离线评测支撑，是检索测试页上人工对比调出来的。**这正是我需要补评估体系的原因。**
3. *相似度阈值和 top_k，哪个更该先调？* → 要点：先调 top_k 找到"召得回来"的区间，再调阈值压噪声。反过来调会先被阈值卡死，看不到召回上限。
4. *同一个 query 在不同 embedding 模型下阈值可以复用吗？* → 要点：不能。不同模型的相似度分布完全不同，换模型必须重新标定阈值。

### Q11：你怎么衡量 RAG 的效果？有没有评估集？

**考察意图**：⚠️ 简历写了 Recall@K/MRR/p95 但代码里没有。**这是必问且必须诚实的问题。**

**参考回答**：
> 我要先纠正我自己简历的表述，这块写得夸大了。
>
> **现状**：我有指标**埋点**（`ai_interview_rag_requests_total`、`ai_interview_rag_duration_seconds`，按 retriever 和 mode 打标签），能观测线上检索的**请求量和延迟**；也有一个管理端的检索测试页做人工对比。但**我没有做成离线批量评估脚本，也没有 Recall@K / MRR / p95 这三个指标的实际产出**。简历上这条写在我"计划做"的位置，是我的表述错误。
>
> **为什么这件事重要**：检索质量没有量化指标，参数调优就全是拍脑袋。我改成 hybrid + RRF 之后，其实是靠检索测试页人工看结果判断变好了，这不可复现、也不能用于回归测试。**改了切分参数或者换了 embedding 模型，我无法自动判断是变好还是变坏**——这是这个项目最大的方法论缺陷。
>
> **如果现在让我补**：① 从题库里抽 200~500 条，人工标注「问题 → 正确 chunk id / question id」；② 写脚本对每个 query 跑检索，算 Recall@K（召回内容有没有包含正确答案）、MRR（第一个正确答案的排名倒数）、p95 延迟；③ 支持按 mode 和参数组合跑，输出对比表；④ 接进 CI，参数改动必须跑一次看有没有回退。

**追问链**：
1. *Recall@K 的 K 怎么定？* → 要点：按下游消费量定。我的下游是"召回候选 → 再筛/再 rerank → 取 final k"，所以评估要看 `recall@20`（召回容量）和 `recall@4`（最终可用量）两个口径。
2. *MRR 和 Recall 的取舍？* → 要点：Recall 看"有没有召回来"，MRR 看"排得够不够前"。检索结果要直接入 prompt 时更关心 MRR（排后面会被截断），只做候选池时更关心 Recall。
3. *p95 比平均延迟更重要吗？* → 要点：是。平均值会被大量快请求掩盖，用户体验由长尾决定。p95/p99 才是 SLO 依据。
4. *LLM 参与的链路怎么评测？* → 要点：LLM 有随机性，评测要用固定 temperature（或 0）+ 固定 prompt 版本 + 多次采样看方差。我另一个行程规划项目做的"冻结评测集 + 规则评测器"就是这个思路，成熟度更高——**这一句能救场，把话题引到你真正做过评估的项目上**。
5. *如果没有标注数据，怎么低成本起步？* → 要点：用 LLM 生成候选标注再人工抽检（LLM-as-judge + 人工校准），比纯人工标注快得多；但要抽查误标率。

### Q12：向量维度是 1024，为什么用这个维度？pgvector 的索引建了吗？

**考察意图**：考察你对 RAG 底层存储的真实掌握度。很多只会调 API 的人这题答不上来。

**参考回答**：
> 1024 是 `text-embedding-v3` 的输出维度，我建向量列时按这个维度固定（`Vector(1024)`）。维度是模型决定的，不是我能选的——换 embedding 模型必须同时改列定义并重建全部向量，这是个代价很高的操作。
>
> pgvector 支持两种索引：**IVFFlat** 和 **HNSW**。IVFFlat 建得快、占内存少，但需要先有数据才能建（要对数据做 K-means 聚类分桶），查询时扫 `nprobe` 个桶；HNSW 是图索引，查询更快更准、增量插入友好，代价是内存占用和建索引时间都更高。
>
> **诚实说，我项目里 vector 列是建了，但索引这块我没有做严格验证**——数据量还小（几千 chunk 量级），走全表顺序扫描的延迟也能接受，所以这个问题没有真正暴露出来。如果数据量上到百万级，必须上 HNSW 并调 `ef_search`。这是我明确知道的、还没验证的短板。

**追问链**：
1. *顺序扫描和索引扫描差在哪？* → 要点：顺序扫描是 O(N) 精确计算所有向量距离，结果精确但线性增长；索引是近似最近邻（ANN），牺牲一点点召回率换数量级的速度提升。
2. *HNSW 的 ef_search / m 参数含义？* → 要点：`m` 是每个节点的连边数（决定图密度和内存），`ef_search` 是搜索时的候选队列大小——越大越准越慢。属于典型的质量/速度旋钮。
3. *pgvector 和专用向量库（Milvus / Qdrant）怎么选？* → 要点：pgvector 的优势是**和业务数据同库，能在一个 SQL 里做向量过滤 + 结构化过滤 + 事务**，运维成本低。缺点是数据量大（千万级）之后性能和扩展性不如专用库。我的场景还得按 category、difficulty、岗位标签做过滤，pgvector 的混合查询正好合适，所以选它是对的。
4. *向量列能不能加普通 B-tree 索引？* → 要点：不行，B-tree 不支持高维向量的距离排序，必须用向量专用索引。
5. *换 embedding 模型要怎么迁移？* → 要点：不能原地改——新旧向量空间不可比。必须**新建列或新表、全量重算、双写或原子切换**。这刚好是我"版本化索引"设计要解决的问题。

### Q13：检索召回不准的时候，你的排查顺序是什么？

**考察意图**：实战排障题，考察你的方法论有没有层次。

**参考回答**：
> 我会由下往上分四层查，因为越靠下的层出错，影响范围越大。
>
> **第一层，数据层**：先确认**正确答案在不在库里**。如果知识库里压根没有这块内容，那是数据覆盖问题，调什么参数都没用。还要看原始文档解析有没有丢内容（PDF 表格、公式最容易丢）。
>
> **第二层，切分层**：答案在库里但召不回，看是不是被切碎了。把目标 chunk 捞出来人眼看一下，是不是语义被切断。这是 `chunk_size/overlap` 的锅。
>
> **第三层，检索层**：切分没问题就换模式试。纯 dense 召不回的专有名词，切 keyword 或 hybrid 能不能召回；能召回但排名靠后就上 rerank；阈值卡太死就临时放宽 `min_score` 看会不会漏。
>
> **第四层，query 层**：前三层都正常，那就是**用户问法和文档表述的措辞差太远**。这时候上 `advanced` 模式的查询改写，让模型把问题改写成更适合检索的形式。
>
> 实操上我会用管理端的检索测试页逐层验证，因为它能并排看不同模式的结果，比翻日志快得多。

**追问链**：
1. *怎么确认是"库里没有"还是"检索不出来"？* → 要点：直接对 chunk 表做全文 `LIKE` 或 `tsquery` 精确搜关键词。能搜到就是检索问题，搜不到就是数据问题。
2. *PDF 解析丢内容怎么发现？* → 要点：入库时对比"原始字符数 vs 解析后字符数"，比例异常就告警；另外 PDF 解析后要保 page number 元数据，方便回溯到原文页。
3. *你怎么知道是召回数量不够还是排序不对？* → 要点：把 `top_k` 临时拉到 100，如果正确答案在里面 → 排序问题（上 rerank）；不在 → 召回问题（改切分/换检索方式）。
4. *线上怎么发现检索质量下降？* → 要点：这是我缺的一环。可以做"下游采纳率"代理指标（召回的题目最终被选中生成的比例）、以及用户对题目"不相关"的反馈按钮。

### Q14：RAG 会不会把简历里的敏感信息拼进 prompt？数据隐私怎么处理？

**考察意图**：企业级 AI 应用的高频合规问题，尤其你的目标客户是"培训机构和企业招聘"。

**参考回答**：
> 这是个真问题，简历是强 PII 数据。
>
> 我目前做的：简历解析结果按 `user_id` 隔离存储、接口层有 JWT 鉴权；Agent 的长时记忆我用 `PostgresStore` 按 user 维度做了命名空间隔离（`memory.py` 里是 privacy-scoped 的设计）；日志里我不存 prompt 全文，只存摘要和 hash。
>
> **我明确没做完的**：① 没有对送入模型的文本做 PII 脱敏（手机号、身份证、邮箱会原样进入 prompt）；② 没有和模型供应商做数据处理协议层面的确认，DeepSeek/DashScope 的调用是否用于训练、留存多久，我没有在项目里做任何技术或流程上的约束；③ 没有数据删除的完整链路（用户注销后向量库里的简历向量怎么清）。
>
> 这是"能跑通"和"能商用"之间的差距，也是我意识到需要补的重点。

**追问链**：
1. *PII 脱敏怎么做？* → 要点：正则 + NER 模型识别手机号/身份证/邮箱/住址，替换成占位符再送模型，回填在本地做；代价是模型对"某市某公司"这类实体的推理会变弱。
2. *多租户下数据隔离怎么做才不会出错？*（**这题会顺势接到你的多租户虚点，见 Q19**）
3. *向量库里怎么删数据？* → 要点：按 `document_id` 外键级联删除 chunk（我模型里 `ondelete="CASCADE"`），但要保证 delete 和向量索引进度一致。
4. *日志脱敏漏了一条会怎样？* → 要点：PII 进日志文件后很难回收，且日志常被采集到第三方平台。所以原则是**日志层做白名单，只记结构化字段，不记原始文本**。

### Q15：你的"模型网关"是怎么统一封装不同供应商的？

**考察意图**：⚠️ **简历虚点。** 代码里只有一个硬编码的 DeepSeek 客户端，没有 provider 抽象。**必须降级说。**

**参考回答**：
> 这个表述我也要修正。目前**没有做出真正的多供应商模型网关**——实际上是一个统一的 AI 服务层（`AIService`），里面用 OpenAI SDK 指向 DeepSeek 的兼容 endpoint，好处是**换兼容 OpenAI 协议的模型只需改 base_url 和 model 名，不用改调用代码**。这算是网关的雏形，但不是完整的网关。
>
> 我**设计了但没实现**的部分：provider 注册表 + 统一接口（`chat / embed / 模型能力声明`）、Fake provider（离线测试和 CI 用，避免测试依赖真实 API 和花钱）、会话级模型配置（不同面试用不同模型做 A/B）。
>
> 我**已经做的一层**是**调用稳定性**：超时（`LLM_TIMEOUT_SECONDS=60`）、指数退避重试（tenacity，最多 3 次）、失败降级到 fallback 结构。这些是**真的**。
>
> 而"**熔断**"这一条，我确实没有实现——没有熔断器、没有失败率统计、没有半开状态恢复。简历这条写得不准。

**追问链**：
1. *熔断和重试的区别？* → 要点：重试是"这次失败了再试一次"，面向**偶发**故障；熔断是"连续失败到阈值就快速失败、不再发请求"，面向**持续性**故障，目的是止损、防止雪崩和无效等待。重试解决不了下游已经挂了的情况，反而会放大压力。
2. *熔断器三态是什么？怎么实现？* → 要点：Closed（正常放行，统计失败率）→ Open（超过阈值，直接拒绝）→ Half-Open（超时后放少量请求试探，成功则回 Closed，失败回 Open）。可以用 Redis 计数做分布式版本，或用 `pybreaker` 这类库。
3. *没有熔断现在会怎样？* → 要点：模型 API 挂掉时，每个请求都会硬等 60 秒超时再重试 3 次，**用户端直接卡死、worker 线程被占满**，故障从模型侧蔓延到整个服务。这是很现实的雪崩路径。
4. *那你怎么至少缓解一下？* → 要点：最简做法是加一个 Redis 共享的失败计数器，5 分钟窗口内失败率超 50% 就直接返回 fallback 不再发请求。工作量很小，收益很大。
5. *Fake provider 有什么用？* → 要点：让测试不依赖外部 API——单测能跑、CI 不会因限流挂掉、也不产生费用。**我这个项目的测试（`tests/`）就是受这个限制，覆盖不到真实模型链路。**

### Q16：Celery 你是怎么用的？任务重复执行怎么办？失败了怎么办？

**考察意图**：考察异步任务的真实工程细节，这题区分度很高。

**参考回答**：
> 我用 Celery + Redis 承载知识库摄⼊、批量向量化、索引重建这类耗时任务，worker 和 beat 分开部署，还挂了 flower 做任务监控。
>
> 三个关键点：
>
> **幂等**：这是异步任务的核心。同一个文档被重复触发索引，不能产生双份 chunk。我的做法是索引前按 `document_id` 先删旧 chunk 再重建，让操作可重复执行结果一致；chunk 表里还有 `content_hash` 字段，可以做内容级去重。
>
> **失败可见**：任务失败不能静默。文档有 `status` 状态机（`pending → indexing → indexed / failed`），失败时把 `error_message` 写回文档记录，管理端能直接看到哪个文档挂了、为什么挂——比翻 worker 日志高效得多。
>
> **超时和重试**：外部调用的任务（embedding 批处理）要设超时和有限次重试，否则一个卡住的任务会占着 worker 不放。

**追问链**：
1. *Celery 的 ack 机制是什么（late ack）？* → 要点：默认 worker 拿到任务就 ack，进程崩了任务就丢了。开 `task_acks_late=True` 变成任务执行完才 ack，崩了会重投——但代价是**必须保证幂等**，否则会重复执行。这是典型的取舍。
2. *beat 和 worker 为什么要分开部署？* → 要点：beat 是单点调度器，如果多副本会重复触发定时任务；worker 可以水平扩容。混在一起会导致调度器多实例冲突。
3. *多 worker 并发做向量化，会不会重复调用 embedding API？* → 要点：可能，如果同一个文档被并发触发。缓解是加分布式锁（Redis SETNX）或按文档路由到固定队列。
4. *任务队列积压怎么发现？* → 要点：我有 `ai_interview_celery_tasks_total` 按 task + status 打点的指标，但**没有配告警规则**，所以现在是"有数据没人看"。要补的是队列长度和失败率阈值告警。
5. *为什么不用 FastAPI 的 BackgroundTasks？* → 要点：进程内、不持久化、没有重试、多副本不同步、进程重启任务就没了。只适合"发个通知"这种丢了也无所谓的场景。

### Q17：简历写"版本化索引原子激活"，这个机制具体是怎么实现的？

**考察意图**：⚠️ **简历虚点。** 代码是原地重建，没有版本化和原子切换。**必须降级说，而且这题你有机会展示"我懂为什么应该这么做"。**

**参考回答**：
> 这条我也要修正。**现状是原地重建**：`reindex_document` 把文档状态置为 `indexing`，删掉旧 chunk，重新切分、向量化、写入，最后置 `indexed`。有一个 `is_active` 标记控制检索时是否参与，但这**不是版本化，也没有原子激活**。
>
> **现状的问题很明显**：重建过程中间态是"没有 chunk"或者"只有一半 chunk"，这时候如果有用户来检索，**要么什么都召不到，要么召到不完整的索引**。而且失败时（比如向量化中途 API 挂了）旧索引已经被删了，只能从头再来。
>
> **我设计的正确方案**（含我另一段后训练项目的经验）：给 chunk 加 `index_version`（或用独立的 `index_versions` 表记 `document_id / version / status / created_at`）。重建时**写新版本，不碰旧版本**；全部完成并校验通过后，在一个**事务里**把 `active_version` 指针切到新版本——这一步是 O(1) 的元数据更新，天然原子。切换前检索读旧版本，切换后读新版本，**不存在空窗期**。失败就丢弃新版本，旧版本照常服务。回滚也只是把指针切回去。
>
> 我在另一个行程规划项目里做过类似的事——**checkpoint 贴角色标签 + 按 `strictness` 动态路由上线 + 保留备版本可回退**，思路是同一套：**让"上线"变成一个原子操作，而不是一堆原地修改。**

**追问链**：
1. *为什么不直接 rename 表？* → 要点：PostgreSQL 的 DDL rename 也要锁表，且会打断正在执行的查询；用指针 + 版本号更轻、更安全，还能保留多版本做灰度。
2. *切换时正在跑的检索怎么办？* → 要点：读旧版本 finish 就行，因为旧版本数据还在（只是不再是 active）。这就是"不原地改"的核心价值。
3. *多版本怎么清理？* → 要点：只保留 active + 上一个版本，其余定期删除；删除要按版本号整批删，避免残留。
4. *切换要不要校验？* → 要点：要。至少校验新版本 chunk 数量 > 0、抽样做一次检索能召回预期结果，否则可能切到一个空索引上。
5. *双写 vs 版本切换？* → 要点：双写简单但两次写不是原子的，且成本翻倍；版本切换更重但切换点明确。数据量大的场景版本切换更稳。

### Q18：为什么用 Alembic？迁移出问题怎么回滚？

**考察意图**：看你有没有真实的数据库变更管理经验。

**参考回答**：
> 这个项目表结构一直在演进（简历、面试、题库、知识库、岗位模板、外部数据源、waiting list……我有 9 个迁移版本），用 Alembic 是为了让本地开发和生产环境的 schema 状态可追溯、可复现，而不是靠手工改表。
>
> 每次变更我按"加表/加字段/加索引"拆成独立迁移文件，每个文件有 upgrade 和 downgrade 两个方向。加字段尽量给默认值，避免已有数据插入失败。
>
> 回滚用 `alembic downgrade -1` 回上一个版本。但有个前提：**downgrade 必须真的写好并测过**，否则出事时回不去——我目前的习惯是每个迁移写完后本地跑一次 upgrade + downgrade 验证。

1. *加一个 NOT NULL 字段到有数据的表上，会出什么问题？* → 要点：已有行没有值会直接失败。要先加 nullable 字段 → 回填数据 → 再加约束，分三步三个迁移。
2. *大表加索引会锁表吗？* → 要点：PostgreSQL 加索引默认会阻塞写。生产要用 `CREATE INDEX CONCURRENTLY`（不阻塞写但更慢、失败会留下无效索引）。
3. *迁移和代码部署的顺序？* → 要点：必须先迁移后部署新代码（兼容性优先），且迁移要**向后兼容**——新代码能读旧结构，旧代码能读新结构，否则滚动发布期间会报错。
4. *Alembic 和 SQLAlchemy model 不一致怎么办？* → 要点：用 `alembic autogenerate` 对比，但 autogenerate 会漏东西（比如列类型修改、索引重命名），必须人工 review，不能盲信。

### Q19：你的多租户隔离是怎么实现的？tenant_id 加在哪一层？

**考察意图**：🔴 **最危险的虚点。** 代码里 `tenant_id` 出现 **0 次**，角色只有两种。面试官问"租户隔离怎么实现"，如果答"每张表加 tenant_id"，下一句一定是"哪个文件？带我看下"——你就完了。

**正确策略：直接如实说，并把话题转到你真做过的权限隔离 + 你设计过的方案。**

**参考回答**：
> 这条我要严肃纠正——我的简历在这一点上夸大了。**这个项目目前没有实现租户隔离，代码里没有 `tenant_id`，也没有 `tenant_admin / content_manager / analyst` 这几种角色。**
>
> **实际做的是 RBAC 的雏形**：管理端只有 `superadmin` 和普通 admin 两种角色。`superadmin` 能创建管理员、看全部管理员列表、改他人信息；普通 admin 只能看和改自己（`admin.py` 里就是 `if current_admin.role != "superadmin" and current_admin.id != admin_id` 这种显式判断）。用户端的数据按 `user_id` 做了归属校验。
>
> **为什么这么写**：我一开始的目标就是单机构部署（培训机构/企业各自部署一套），所以按单租户设计。写到简历上是我对"企业级能力"的理解过度包装了，抱歉。
>
> **如果要改成真正的多租户，我知道该怎么做**：① 所有业务表加 `tenant_id` 并建复合索引（`tenant_id` 打头）；② 用 FastAPI 的依赖注入把 tenant 上下文注入请求，**不靠每个接口手写过滤条件**——因为手写一定会漏，漏一个就是跨租户数据泄露；③ 更稳的做法是用 PostgreSQL 的**行级安全策略（RLS）**，在数据库层强制过滤，应用层忘了写条件也拦得住；④ 鉴权改成 `role + permission` 的细粒度模型（`content_manager` 只能管题库知识库、`analyst` 只读报表），而不是现在的角色字符串硬编码判断。

**追问链**：
1. *为什么说"每个接口手写过滤"一定会漏？* → 要点：新增接口时容易忘；而且复杂查询（join、聚合、导出）里过滤条件容易写错位置。这是安全设计的"默认安全"原则——**默认拒绝，而不是默认放行**。
2. *PostgreSQL RLS 怎么用？* → 要点：`ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + 建 policy 用 `current_setting('app.tenant_id')` 做条件，连接时用 `SET app.tenant_id = xxx` 注入。应用层代码完全不用改，DB 层兜底。
3. *租户数据放一个库还是一个库一个租户？* → 要点：共享库 + tenant_id 成本最低、运维简单，但隔离性弱、有噪声邻居问题；独立库隔离强但运维成本高、跨租户统计难。中小规模共享库，合规要求高（金融/医疗）就独立。
4. *现在这个角色模型有什么具体问题？* → 要点：角色硬编码在业务代码里，加角色要改代码；权限判断散落在各接口，容易不一致；没有权限粒度的统一声明。
5. *跨租户统计报表怎么做？* → 要点：单独走一条带更高权限的查询路径，或做数据同步到分析库，而不是放宽主库的 RLS。

### Q20：Prometheus 和 Alertmanager 你是怎么接的？告警规则配了哪些？

**考察意图**：🟠 简历虚点。指标埋点是真的、很完整，但 compose 里没有 Prometheus / Alertmanager 服务，也没有任何告警规则文件。

**参考回答**：
> 我要区分两部分说，因为这两部分成熟度不一样。
>
> **做好的部分是指标埋点**，这个是真的、而且比较完整：我用 `prometheus_client` 建了一套指标，覆盖四层——API 层（`ai_interview_api_requests_total` 按 method/path/status、`api_request_duration_seconds` 直方图）、LLM 层（请求数 + 延迟）、RAG 层（按 retriever 和 mode 分别打标）、Celery 层（按 task + status）、Agent 层（`agent_runs_total` 按 status、`agent_node_duration_seconds` 按 node）；另外还有长时记忆操作数和 advanced RAG 操作数的计数器。有 `METRICS_ENABLED` 开关控制 `/metrics` 是否暴露。

>
> **要补的话**：加 prometheus 服务抓 `/metrics`，写 record rules 做聚合，加 alert rules——比如 `LLM 错误率 5 分钟 > 5%`、`Agent 运行失败率 > 10%`、`RAG p95 延迟 > 3s`、`Celery 队列积压 > 100`、`任务失败率 > 5%`，配 Alertmanager 做分组、抑制和通知路由。

**追问链**：
1. *Counter 和 Histogram 的区别？* → 要点：Counter 只增不减（累计请求数、错误数）；Histogram 统计分布（延迟分桶），能算分位数。**延迟必须用 Histogram，不能用 Counter 做平均**——平均值会掩盖长尾。
2. *Prometheus 的拉模型（pull）和推模型（push）？* → 要点：Prometheus 默认是 pull，定时来抓 `/metrics`。短生命周期任务（比如一次性脚本）用 Pushgateway 推。我的 Celery 任务用 pull 就行，因为 worker 长期存活。
3. *指标标签（label）设计有什么坑？* → 要点：**不能把高基数（high cardinality）的值当标签**。比如把 `user_id`、`run_id` 当标签，会让时间序列数量爆炸，Prometheus 直接被拖垮。我的 path 标签也是要小心的地方，带 ID 的路径必须先归一化（`/interviews/{id}` 而不是 `/interviews/123`）。
4. *histogram 分桶怎么选？* → 要点：按 SLO 定。如果目标是 p95 < 2s，桶就要在 0.1/0.5/1/2/5 附近密集分布，不能全挤在 0.05。
5. *Alertmanager 的抑制（inhibition）和静默（silence）？* → 要点：抑制是"上层故障时压掉下层的衍生告警"（比如整个服务挂了，就不用报每个接口 5xx）；静默是计划内维护期的临时关闭。**没有这两者，告警风暴会把值班的人淹没。**

### Q21：你的登录限流怎么做的？限流算法选的是哪种？

**考察意图**：这是你真做了的点（`RATE_LIMIT_ENABLED` / `RATE_LIMIT_FAIL_OPEN`），要答好，因为它是你"基础设施意识"的证据。

**参考回答**：
> 登录限流是保护账号不被暴力破解，我用 Redis 做计数窗口，按账号/IP 维度限制单位时间内的失败次数，超过就返回统一的错误提示。有两个开关：`RATE_LIMIT_ENABLED` 控制是否开启，`RATE_LIMIT_FAIL_OPEN` 控制 Redis 不可用时的行为——默认是 **fail-closed（拒绝请求）**，因为限流是安全能力，挂掉时不能变成"全放行"。
>
> 这是个明确的取舍：安全场景 fail-closed，可用性优先的场景（比如只是防刷的普通接口）可以 fail-open。我把它做成配置项，就是因为不同接口的取向不同。

**追问链**：
1. *固定窗口、滑动窗口、令牌桶、漏桶怎么选？* → 要点：固定窗口实现最简单但有**临界问题**（窗口边界两侧各打一轮，瞬时能过 2 倍量）；滑动窗口解决临界问题但内存占用更高；令牌桶允许突发、漏桶强制匀速。登录防爆破用滑动窗口或令牌桶都合适。
2. *分布式限流怎么做？* → 要点：计数器必须放 Redis 共享，不能用进程内存（多副本会各限各的，等于限制放宽 N 倍）。用 Lua 脚本保证"读-判断-写"原子，否则并发下会超限。
3. *为什么错误提示要统一？* → 要点：区分"账号不存在"和"密码错误"会泄露账号是否存在，便于攻击者枚举有效账号。所以统一成"账号或密码错误"。
4. *限流的 key 设计要注意什么？* → 要点：要同时按账号和 IP 限（只按 IP 挡不住分布式 IP 的撞库，只按账号挡不住对多账号的撞库）；key 要设过期时间，否则内存泄漏。

### Q22：你说"保障生产可用性"，具体做了什么？可用性怎么度量？

**考察意图**：考察你有没有"生产"这个概念，还是只会跑本地。

**参考回答**：
> 实际做的：**健康检查**是完备的——app、celery worker、celery beat、postgres、redis、nginx 都有 healthcheck，`/api/v1/config/health` 作为 app 的探针，`depends_on` 用了 `condition: service_healthy` 保证启动顺序（等数据库就绪再起应用），`restart: unless-stopped` 保证崩溃自愈。日志按小时滚动、保留 7 天，前后端静态资源分离部署。
>
> **没做的**：没有做多副本和负载均衡（目前都是单副本），没有做数据库的主从和故障转移，没有做 pg_dump 备份策略——**简历上写的"PostgreSQL 自动备份"我实际没做**，这条也是不准确的。
>
> **可用性怎么度量**：应该用 SLI/SLO——SLI 是"成功率 = 非 5xx 请求 / 总请求"和"p95 延迟"，SLO 是"月成功率 ≥ 99.9%"，再用错误预算（剩余可失败额度）来驱动发布决策。**我目前只有指标埋点的原料，没有定义 SLI/SLO，也没有基于错误预算的发布门禁。**

**追问链**：
1. *健康检查深探（deep）和浅探（shallow）的区别？* → 要点：浅探只确认进程活着；深探要验证依赖可用（能连上 DB、Redis）。但深探有风险——依赖抖动会让所有副本同时被判定不健康然后被重启，反而放大故障。通常 liveness 用浅探、readiness 用深探。
2. *start_period 和 interval 为什么要设？* → 要点：应用启动要时间（加载模型、建连接池），`start_period` 让容器在这段时间内的失败不计入重试次数，避免启动慢被反复杀掉。
3. *99.9% 意味着多少不可用时间？* → 要点：每月约 43 分钟。每提升一个 9，架构成本上升一个量级——**这是必须知道的换算，答不上来会显得没有工程感觉。**
4. *单副本的致命问题是什么？* → 要点：部署时必然服务中断（滚动发布做不了）、单点故障无法自愈到新实例、无法承受流量峰值。要上多副本就必须解决**无状态化**——会话、限流计数、任务状态都不能放进程内存。
5. *你的 checkpoint 是进程本地的吗？* → 要点：不是，`AsyncPostgresSaver` 落 PG，所以**Agent 状态是跨副本共享的**，这是多副本改造的一个好基础。但 `runtime.py` 是"process-local runtime"，连接池是进程级的，多副本时每个副本各建一个池，需要在连接数预算上留余量。

### Q25：如果我要你把面试环节改成真正的自适应追问，你怎么设计？

**考察意图**：考察迁移和设计能力，也考验你前面承认的缺口能不能补上。

**参考回答**：
> 我会把它改成一个 LangGraph 图，而不是现在的顺序 service：
>
> 节点：`load_context → plan_question → ask（interrupt 挂起等回答）→ evaluate_answer → 路由判断 → {follow_up | next_question | finish} → generate_report`。
>
> 关键设计：
>
> **判断条件不用模型拍脑袋**，而是用结构化信号：`evaluate_answer` 输出的 `score` 低于阈值、或者 `AnswerEvaluation` 里明确标出"缺失了 X 采分点"、且**追问次数还没超过上限**（比如单题最多追 2 次，防止死循环）→ 走 `follow_up` 分支。
>
> **追问的内容生成**要有依据：不是让模型随便换个问法，而是把"参考答案里这个候选人没提到的采分点"作为追问目标喂进去，问"你刚才没提到 X，能具体说说吗"。这样追问才是有信息量的，而不是重复问。
>
> **难度调整**做成状态机：连续 N 题均分高于阈值就升档，低于就降档，档位映射到 RAG 召回的 `difficulty` 过滤条件。
>
> **为什么必须用图**：因为面试是 **human-in-the-loop**，要在"问完题"处挂起。LangGraph 的 `interrupt` + checkpointer 能保证用户关掉页面、明天回来接着答，状态还在。现在用 service 实现做不到——请求断了状态就散在 DB 里，越写越乱。

**追问链**：
1. *怎么防止追问死循环？* → 要点：硬上限（单题追问 ≤ 2 次）+ 状态里记 `follow_up_count`，超限强制进下一题。**任何自主循环都必须有硬性终止条件。**
2. *追问让总题数变多了，用户时间成本怎么控制？* → 要点：追问计入总题数配额，或者主问题减少、追问补齐配额，保持总时长可控。
3. *怎么评测追问质量？* → 要点：人工标注"这个追问是否指向了缺失的采分点"，算准确率；退一步可以看追问后重答的分数提升幅度——**提升明显说明追问问到了点上。**
4. *这会不会让不同用户的面试不可比？* → 要点：会，这是自适应面试的本质代价。解决办法是报告里对难度做归一化，或者保留固定题组做基准对照。
5. *改造成图之后，你现在的卡片/流式输出怎么办？* → 要点：图节点内部仍然可以用 SSE 流式吐给前端，图负责的是**状态流转和持久化**，两者不冲突。我项目里报告生成已经是流式的，可以复用。

### Q26：这个项目上线能扛多少并发？瓶颈在哪？

**考察意图**：压力测试题，考察你对性能瓶颈的判断力。**答不上来比答错更糟。**

**参考回答**：
> 我没做压测，所以**没有实测数据**，这是实话。但我可以给出它必然的瓶颈和量级判断。
>
> **瓶颈一定在 LLM 调用，不在数据库。** 一次完整面试的 LLM 调用次数不少：简历解析 1 次、画像抽取 1 次（Agent 节点）、题目生成可能 1~2 次（含补全）、每题评分 1 次、报告生成 1 次，再加上 rerank。**如果 5 道题，单次面试就是 10 次以上的模型调用。** 每次调用哪怕 3 秒，用户等待也是几十秒起步。
>
> **所以结论是**：这个系统扛不住的是"同时有很多人在面试"，不是"数据库慢"。单副本 FastAPI 的 async 能撑住并发连接，但**并发连接不等于并发吞吐**——真正排队的是模型 API 的配额和响应时间。
>
> **对策**：① 能异步的都异步（简历解析、向量化已经用 Celery 了，但面试中的评分还没完全异步化）；② 评分不要每题都串行调模型，可以攒批或者预生成；③ 缓存——简历解析结果、画像结果明显可以缓存（同一份简历重复解析没意义）；④ 如果有条件，用更小更快的模型做评分、大模型只做出题；⑤ 加并发上限保护（信号量），防止模型 API 被自己打挂。

**追问链**：
1. *怎么找到真正的瓶颈？* → 要点：先压测再优化。用 locust/k6 打接口，配合指标看 p95，先分清楚是"等模型"还是"等 DB"还是"CPU 密集"。**别凭感觉优化。**
2. *数据库会先扛不住吗？* → 要点：不会，除非向量检索数据量大。pgvector 顺序扫描在几千 chunk 量级是几十毫秒，还能接受；到百万级才需要 HNSW。关系查询都有索引，不是瓶颈。
3. *SSE 长连接会占多少资源？* → 要点：async 下一个 SSE 连接占用很小，但**每个连接背后挂着一个模型调用**，所以真正的成本还是模型侧。要注意反向代理的超时设置（Nginx 默认 60s 会掐断长流式响应，必须调 `proxy_read_timeout`）。
4. *怎么提高模型调用的并发效率？* → 要点：无依赖的调用用 `asyncio.gather` 并发；有依赖的拆成阶段；控制并发度避免触发供应商限流（429）。
5. *限流和降级在过载时的表现？* → 要点：要设计**过载时的优先级**——登录、提交答案这种核心链路保，报告生成、知识库重建这种可以让步。目前我没有分级，所有请求一视同仁，过载时会一起变慢。

## 6. 未落地技术点 · 应对知识点包

> 用法：每个"没做"的点，你要掌握**最小知识骨架 + 被追问时的诚实答法 + 能立刻补做的最小实现**。第三列是关键——**能说出"半天能补完"的人，和"我只听说过"的人，评价完全不同。**

### 6.1 熔断器（Circuit Breaker）🔴

| 必须掌握 | 内容 |
|---|---|
| 三态 | Closed（放行，统计失败率）→ Open（快速失败，不发请求）→ Half-Open（超时后放少量试探请求，成功回 Closed，失败回 Open） |
| 触发条件 | 时间窗口内失败率 > 阈值 或 连续失败次数 > 阈值 |
| 与重试的关系 | 重试应对偶发故障，熔断应对持续故障。**没有熔断的重试会放大故障** |
| 与降级的区别 | 熔断是"停止调用"，降级是"给一个兜底结果"。通常熔断后触发降级 |
| 分布式实现 | 状态必须跨副本共享 → 用 Redis 计数，Lua 保证原子 |
| 落地工具 | 单进程用 `pybreaker`；要跨副本就用 Redis 自己写（很简单：一个窗口计数器 + 三个状态 key） |

**被追问时的诚实答法**：我没实现熔断，只做了超时 + 重试 + 兜底。我知道没有熔断的风险是：模型 API 挂掉时每个请求都要硬等 60 秒超时再重试 3 次，worker 会被占满，故障从模型侧蔓延到全站。

**最小补做（半天）**：写一个 `CircuitBreaker` 类，用 Redis 存 `fail_count` / `state` / `opened_at`；在 `AIService._chat` 前包一层判断；Open 状态直接抛异常走现有 fallback 逻辑。三个状态 + 一个滑动窗口计数，不到 100 行。

| 必须掌握 | 内容 |
|---|---|
| 抽象什么 | `chat()` / `embed()` / 能力声明（上下文长度、是否支持 JSON mode）/ 用量返回（token 数、成本） |

### 6.3 离线评估脚本（Recall@K / MRR / p95）🔴

| 必须掌握 | 内容 |
|---|---|
| Recall@K | 前 K 条里包含正确答案的比例。衡量"召得回来吗" |
| MRR | 第一个正确答案排名的倒数（1/rank）的平均值。衡量"排得够前吗" |
| p95 延迟 | 95% 的请求快于这个值。**比平均值重要**，平均值会被长尾掩盖 |
| 评估集构造 | 从题库/知识库抽样，「query → 正确 chunk_id / question_id」标注对；没有人工标注时用 LLM 生成候选再人工抽检 |
| 冻结评测集 | 参数调优期间**不修改**评测集，否则就是自己给自己出考卷（这个问题我在另一个项目里踩过，有成熟方案） |
| 对比维度 | 按检索模式（semantic/keyword/hybrid/advanced）、按 chunk_size、按 embedding 模型分别跑，输出对比表 |
| 接 CI | 参数变更必须跑评估，指标回退则阻止合并 |

**被追问时的诚实答法**：这个我没做，简历上写的是我的计划。后果是：我改了切分参数或者换了检索模式，**无法自动判断是变好还是变坏，全靠人眼看测试页**，不可复现也不能做回归。**这是这个项目方法论上最大的缺陷。**

**最小补做（1~2 天）**：抽 200 条 query 标注 → 写 `scripts/eval_retrieval.py`，对每个 query 调检索，算 Recall@5/20、MRR、延迟 p50/p95 → 输出 Markdown 对比表 → 至少能跑通"hybrid vs dense"的对比，拿到真实数字。**有了真实数字，Q11 就从扣分题变成加分题。**

### 6.4 版本化索引原子激活 🔴

| 必须掌握 | 内容 |
|---|---|
| 问题 | 原地重建有空窗期（检索时索引不完整），失败后旧索引已删，不可回滚 |
| 方案 | 写新版本 → 校验 → **事务内切换 active_version 指针**（O(1) 元数据更新，天然原子）→ 保留旧版本做回滚 |
| 表设计 | `index_versions(id, document_id, version, status, created_at)`；chunk 表加 `index_version` 字段；检索时 join 当前 active 版本 |
| 灰度 | 指针切换可以按比例/按租户灰度，出问题把指针切回去 |
| 清理 | 只保留 active + 上一版，其余按版本号整批删除 |
| 可类比的成熟方案 | 数据库蓝绿发布、K8s 滚动发布、模型 checkpoint 角色标签下发。**本质都是"让上线变成原子操作，而不是原地修改"** |

**被追问时的诚实答法**：我做的是原地重建（删旧 chunk → 重新切分向量化 → 写新 chunk），有 `status` 状态机但没有版本化、没有原子切换。问题是重建期间检索会看到不完整的索引，失败后旧索引已经删了回不去。

**加分点**：你另一个项目的"checkpoint 角色标签 + 按 strictness 动态路由 + 保留备版本可回退"和这个是同一套思想，**主动做这个类比，会显得你有方法论而不是只会一个技巧。**

**最小补做（2~3 天）**：加 `knowledge_index_versions` 表 + chunk 加 `index_version` 列；重建时写新版本；完成后一个事务更新 document 的 `active_version`；检索加版本过滤；保留上一版本支持回滚。

### 6.5 多租户隔离（tenant_id / RLS）🔴

| 必须掌握 | 内容 |
|---|---|
| 隔离粒度 | 共享库共享表（加 tenant_id，成本最低）vs 独立 schema vs 独立库（隔离最强，运维最重） |
| 关键原则 | **默认拒绝**。靠应用层每个接口手写过滤条件一定会漏，漏一个就是跨租户数据泄露 |
| 数据库层兜底 | PostgreSQL RLS：`ENABLE ROW LEVEL SECURITY` + policy 用 `current_setting('app.tenant_id')`；连接时 SET 注入 |
| 索引设计 | 复合索引 tenant_id 打头，否则查询用不上索引 |
| 鉴权模型 | RBAC（角色）→ 权限点（`resource:action`）→ 细粒度鉴权。角色硬编码在业务代码里是反模式 |
| 常见坑 | 唯一约束要带 tenant_id（否则 A 租户的用户名会撞 B 租户）；异步任务/后台脚本没有请求上下文，tenant 要显式传参；缓存 key 必须带 tenant_id |
| 跨租户统计 | 单独高权限查询路径或同步到分析库，不要放宽主库策略 |

**被追问时的诚实答法**：代码里没有 tenant_id，我是按单租户设计的（培训机构各自部署一套）。角色只有 superadmin 和普通 admin。简历这条是我过度包装了。我理解的正确做法是：表加 tenant_id + 用依赖注入注入租户上下文 + 用 RLS 在数据库层兜底——**因为靠人写过滤条件一定会漏。**

**最小补做（3 天，但要动全部表）**：这个不建议现场承诺能快速补，因为要改所有表和所有查询。**诚实说"这是架构级改动，我评估要一周以上"，反而更专业。**

### 6.6 Prometheus + Alertmanager 告警体系 🟠

| 必须掌握 | 内容 |
|---|---|
| 已完成 | 指标埋点（`prometheus_client`）+ `/metrics` 出口 + `METRICS_ENABLED` 开关 |
| 缺什么 | Prometheus 服务、抓取配置、record rules、alert rules、Alertmanager、通知路由 |
| 核心指标 | API 错误率、p95 延迟、LLM 错误率、Agent 失败率、RAG p95、Celery 队列积压 + 任务失败率 |
| 关键概念 | pull 模型；**label 高基数会拖垮 Prometheus**（不能把 user_id/run_id 做标签）；path 要归一化；Histogram 分桶按 SLO 定；告警要分组 / 抑制 / 静默，否则是告警风暴 |
| SLI/SLO | SLI = 成功率 / p95 延迟；SLO = 月成功率目标；**错误预算**（1 - SLO）驱动发布决策 |
| 换算 | 99.9% ≈ 每月 43 分钟；99.95% ≈ 22 分钟；99.99% ≈ 4 分钟 |

**被追问时的诚实答法**：指标埋点我做完了，而且覆盖 API / LLM / RAG / Celery / Agent 五层；但采集和告警没做——没有部署 Prometheus 和 Alertmanager，没有告警规则。所以准确说是"完成了可观测的埋点基础"，不是"接入了监控告警体系"。

**最小补做（1 天）**：compose 里加 prometheus + alertmanager 服务，写 `prometheus.yml` 抓 app / celery 的 `/metrics`，写 3~5 条 alert rules，配置 webhook 通知。**有了这套，Q20 从虚点变成亮点。**

### 6.7 面试 Agent 图 + 动态追问 🔴

| 必须掌握 | 内容 |
|---|---|
| 为什么必须是图 | 面试是 human-in-the-loop，要在"问完题"处挂起 → LangGraph `interrupt` + checkpointer 才能在服务重启/用户离开后接着答 |
| 节点切分 | `load_context → plan_question → ask(interrupt) → evaluate_answer → route → {follow_up / next / report}` |
| 追问触发条件 | 不用模型拍脑袋：`score < 阈值` 且存在"未覆盖的采分点" 且 `follow_up_count < 上限` |
| 追问内容 | 不是换个问法重问，而是**针对参考答案里候选人没提到的那几个采分点**定向追问 |
| 硬性终止 | 任何自主循环都必须有硬上限，否则死循环烧钱 |
| 难度自适应 | 连续 N 题均分 → 升/降档 → 映射到 RAG 召回的 difficulty 过滤 |
| 与流式输出的关系 | 图管状态流转和持久化，节点内部照样能 SSE 流式吐给前端，两者不冲突 |

**被追问时的诚实答法**：面试环节我只在 schema 和 prompt 里留了 `follow_up` 字段，**业务逻辑从未消费它**，所以追问实际没跑通。难度也是静态传入的，不是根据答题表现实时升降。

**最小补做（2~3 天）**：把 `InterviewService` 的逐题循环抽成图，先实现"评分低于阈值 + 未超上限 → 生成定向追问"这一条分支，用现成的 `AsyncPostgresSaver`。**先跑通一条追问分支，比设计一个完美图更有说服力。**

## 7. 话术红线

**绝对不要说：**
- ❌ "我实现了模型网关，支持多供应商路由" → 代码里只有一个 DeepSeek 客户端
- ❌ "我们用 tenant_id 做了租户隔离" → 代码里 0 处 tenant_id
- ❌ "接了 Prometheus 和 Alertmanager 做告警" → 只有埋点，没有采集和告警
- ❌ "做了熔断降级" → 只有重试
- ❌ "构建了离线评估脚本监测 Recall@K/MRR/p95" → 没有这个脚本
- ❌ "两个 Agent 状态图" → 只有岗位匹配图

**应该改成的说法：**
- ✅ "我做了统一的模型调用层，用 OpenAI 兼容协议，换模型只改配置；熔断是我知道但没实现的"
- ✅ "目前是单租户设计，用 superadmin + admin 的 RBAC 雏形；多租户我了解 RLS 方案"
- ✅ "我完成了五层的指标埋点，采集和告警规则还没配"
- ✅ "做了超时、指数退避重试和格式兜底；熔断器没做，我知道它会走什么雪崩路径"
- ✅ "检索指标我埋了点，但离线评估脚本还没写——这是我最想补的一块"
- ✅ "用 LangGraph 编排了岗位匹配 Agent；面试环节还是 service 顺序流程，重构成图是我的下一步"

**最后一条，也是最重要的**：

你的 RAG 链路是真东西——**RRF 公式、k=60 的来历、chunk 500/50 的取舍、题库 0.7 vs 知识库 0.3 的业务逻辑、pgvector 索引选择、四种检索模式的适用场景**，这些你都答得出来，而且答得比很多工作两三年的人清楚。

**面试策略：主动把话题往 RAG 引。** 当面试官在 Agent 和多租户那侧挖不出东西、开始怀疑项目真实性时，一句"我这边检索链路做得比较深，要不要展开讲讲 RRF 融合和参数设计"——能把面试从"查账"拉回"技术交流"。

**同时，回去改简历。** 六个虚点删掉三个、降级表达三个，你的简历可信度会立刻上一个台阶。面试官不反感没做完，只反感说做了答不上来——而"答不上来"这件事，今天已经把风险点全列给你了。
